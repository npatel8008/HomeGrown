# GardenAI

**Grow what you actually eat.**

GardenAI turns a household's food habits, available space, and local growing
conditions into a personalized garden plan: which crops to grow, how many of
each, why, what they'll yield, what they'll save, where to plant them, and what
to do in the garden today.

This repository is a **working scaffold** with several layers wired up for
real. The full product journey runs end to end. Ingredient extraction and the
"why this crop" rationales run on **K2 (IFM)** when an API key is present, and
location, climate and weather are **live data from Open-Meteo** — no API key
needed. Crop scoring, plant allocation, layout packing and the care rules are
still deliberate placeholders, each isolated so it can be replaced
independently.

Every model-backed path falls back to a deterministic offline implementation on
error, timeout, or unparseable output, and the UI shows which one actually ran.

---

## The product flow

```
Household food habits
  → Ingredient extraction
  → Household food-demand profile
  → Land / climate analysis
  → Crop recommendation engine
  → Financial savings model
  → Garden layout generator
  → 3D garden visualization
  → Ongoing garden monitoring
```

Every stage exists in the app today, backed by placeholder logic.

### The four systems, and why they're separate

The architectural requirement for this project is that these four never share a
code path. Each has its own module, its own route, and its own typed contract:

| # | System | Module | Endpoint |
|---|--------|--------|----------|
| 1 | Ingredient extraction | `services/ingredient_extraction.py` | `POST /api/analyze-food` |
| 2 | Crop recommendation / scoring | `services/crop_scoring.py` | `POST /api/recommend-crops` |
| 3 | Garden layout generation | `services/layout_generator.py` | `POST /api/generate-layout` |
| 4 | Garden care recommendations | `services/care_engine.py` | `GET /api/garden-status`, `GET /api/care-recommendations` |

Route handlers contain no business logic — they validate, delegate, and return.

### What runs on a real model

| Step | Implementation | Source |
|------|----------------|--------|
| Ingredient extraction | **live** when `IFM_API_KEY` is set | `IFM/K2-Think-v2` |
| Crop rationales ("why this crop") | **live** when `IFM_API_KEY` is set | `IFM/K2-Think-v2` |
| Geocoding (city / ZIP → coordinates) | **live**, no key | Open-Meteo geocoding |
| Climate: frost dates, season length, GDD | **live**, no key | Open-Meteo archive |
| Weather: current + 7-day forecast | **live**, no key | Open-Meteo forecast |
| Crop scoring & plant allocation | heuristic placeholder | — |
| Garden layout | shelf-packing placeholder | — |
| Care task rules | heuristics over real weather | — |

`GET /api/health` reports this at runtime, and the UI shows a "Generated by"
badge next to the food profile and the crop list. If a model call fails, the
badge says `built-in heuristic` — the demo never claims to be AI-powered when
it quietly wasn't.

**Model choice.** Both K2 models were measured on the extraction prompt:

| Model | Latency | Behaviour |
|-------|---------|-----------|
| `IFM/K2-Think-v2` | ~4-14s | Clean JSON in `content`, chain-of-thought kept in a separate `reasoning` field. **Default.** |
| `IFM/K2-Horizon-375B-A23B` | ~70s | Spilled 8k tokens of chain-of-thought into `content` and never closed the JSON; also timed out when sent `response_format`. Kept configurable for free-text work. |

Three things were needed to make K2-Think reliable, all in
`services/llm_client.py` and the prompts:

1. **A terse prompt.** Deliberation length scales with prompt complexity — a
   long rule list made it burn its entire budget reasoning and return nothing.
2. **`max_tokens: 16384`.** Reasoning is billed to the completion budget, and
   4k-9k tokens is normal for a small extraction; the server default of 8192
   truncates mid-answer.
3. **One retry** with an "output only the JSON now" nudge. Measured 8/8
   successful extractions with the retry in place.

## Running it locally

You need **Python 3.9+** and **Node 20+**. No database and no network
access required — the demo runs fully offline. An IFM API key is optional and
upgrades two steps from placeholder to real model output. Auth0 is optional
too: without its env vars the app stays public; with them, the garden flow
requires a signed-in user.

### 1. Backend

```bash
cd backend
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env      # optional: add IFM_API_KEY to enable K2
uvicorn main:app --reload --port 8000
```

Interactive API docs: <http://localhost:8000/docs>
Health check: <http://localhost:8000/api/health>

### 2. Frontend

In a second terminal:

```bash
cd frontend
npm install
npm run dev
```

Open <http://localhost:3000>.

To turn on Auth0, copy `frontend/.env.local.example` to `frontend/.env.local`
and fill in the `AUTH0_*` values from a Regular Web Application in the
[Auth0 Dashboard](https://manage.auth0.com/). Register:

- Callback: `http://localhost:3000/auth/callback`
- Logout: `http://localhost:3000`
- Web origins: `http://localhost:3000`

Generate `AUTH0_SECRET` with `openssl rand -hex 32`. Restart `npm run dev`
after changing env vars. Until those four values are set, login is hidden and
every screen stays public.

`next.config.mjs` proxies `/api/*` to the backend on port 8000, so the frontend
talks to its own origin and needs no configuration to run locally. Override the
proxy target with `BACKEND_ORIGIN`, or bypass it entirely by setting
`NEXT_PUBLIC_API_URL` to an absolute `https://` URL once the backend is deployed
separately. Do not point it at `http://localhost:8000` — see
[docs/RUNNING_ON_A_PHONE.md](docs/RUNNING_ON_A_PHONE.md).

### On a phone

Camera, motion and geolocation need HTTPS, so a phone cannot use
`http://<your-ip>:3000`. Run a tunnel and open the URL it prints:

```bash
cloudflared tunnel --url http://localhost:3000
```

Full instructions, including why the API is proxied rather than tunneled
separately: [docs/RUNNING_ON_A_PHONE.md](docs/RUNNING_ON_A_PHONE.md).

### The demo path

1. Landing page → **Use the demo household** (seeds a 4-person household:
   tacos 2×, pasta 2×, salads 3×, omelets 4× per week).
2. **Analyze my food habits** → extracted growable ingredients.
3. Food-demand profile → remove, add, or reweight ingredients.
4. **Growing space** → enter a **ZIP code** (the demo uses 78704) and the city,
   frost dates, season length and hardiness zone fill in automatically. Then
   12 ft × 8 ft, raised beds, beginner, $150.
5. **Recommendations** → ranked crops, yields, savings, homegrown coverage.
6. **Generate garden layout** → 2D planner with beds, paths and spacing.
7. **View in 3D** → the same layout, walkable; click any plant.
8. **Today** → weather, task list, season progress.

### If the backend isn't running

Every API call falls back to `frontend/lib/fallback.json` — real responses
captured from the backend for the demo household — and the UI shows an
"Offline demo mode" banner saying so. The demo never hard-fails mid-presentation,
and it never silently pretends the data is live.

To regenerate that file after changing any backend service:

```bash
cd backend && python scripts/capture_fallback.py
```

## Where the real implementations go

Each swap point is marked in the source with a `>>> REPLACE ME <<<` comment.

```bash
grep -rn "REPLACE ME" backend frontend
```

### 1. AI ingredient extraction — **done**
`backend/services/ingredient_extraction.py`

Two implementations behind one contract: `_extract_with_llm` (K2) and
`_extract_with_keywords` (offline). `extract_ingredients()` picks, and returns
an `ExtractionResult` carrying which one ran. Nothing outside the module knows
the difference.

Remaining work here: the model's `weekly_usage_score` scale drifts between runs
(one returns 100/82/64, another 19.3/15.8/8.8), so the module renormalises the
top ingredient to 100. Few-shot examples would be a better fix than rescaling.
It also occasionally pads the list with score-0 rows, which are dropped.

To point at a different provider, change `services/llm_client.py` — it's the
only module that knows the wire format, and the API is OpenAI-compatible.

### 2. Recommendation algorithm
`backend/services/crop_scoring.py`

Two things should change:
- **Scoring** — `_climate_fit()` currently derives everything from a
  self-reported sunlight level. It should use the ZIP code to look up a
  hardiness zone, frost dates and season length.
- **Allocation** — the greedy loop at the bottom of `score_crops()` should
  become a constrained optimisation over square footage and budget, with
  companion-planting and succession constraints. The weights in `WEIGHTS` and
  the `ScoreBreakdown` contract can stay as they are; only the solver changes.

### 3. Layout generation
`backend/services/layout_generator.py`

The shelf packer is honest about failure: anything that doesn't fit comes back
in `unplaced` and the UI surfaces it. A real version should do proper
bin-packing with companion planting, vertical/trellis space, and sun-path
shading. Note that the 2D planner and the 3D scene both render this exact
response — keep the contract and both views stay in sync for free.

### 4. Weather and climate — **done**
`backend/services/location.py`, `backend/services/climate.py`

Open-Meteo was chosen because it needs no API key and no signup, so the demo
works for anyone who clones the repo. Three endpoints are used:

- **Geocoding** resolves a US ZIP (or a place name) to coordinates, timezone
  and elevation. The form is ZIP-first: a postal code is unambiguous, and the
  city is *derived* from the lookup and shown read-only, so what's on screen is
  always what the scoring engine used. A city-search mode covers places without
  US-style ZIPs, since the geocoder is global.
- **Archive** pulls the last full year of daily weather, from which
  `_derive()` computes the last spring frost, first fall frost, frost-free
  days, growing-degree-days (base 50°F), days over 90°F, summer averages,
  annual rainfall and a USDA-style hardiness zone.
- **Forecast** gives current conditions plus seven days, feeding the care
  engine and the "Today" dashboard.

Both fall back to neutral placeholder data offline, and the `source` field on
each result says which you got.

**What this changed downstream.** Season length is no longer a constant:

- `crop_scoring._season_fit()` treats "can this crop reach harvest before your
  first frost" as a *hard gate* — crops that can't are dropped and reported in
  `skipped` with `kind: "climate"` and a plain-English reason.
- `crop_scoring._temperature_fit()` scores warm-season crops on accumulated
  GDD and cool-season crops on how many days break 90°F, so bok choy outranks
  tomatoes in Anchorage and the reverse holds in Austin.
- Climate's weight in the overall score went from 0.20 to 0.30, because it is
  now measured data rather than an inference from a dropdown.
- Homegrown coverage and the per-crop "appetite cap" both scale with the real
  frost-free window, so a 314-day Austin season implies a much larger seasonal
  produce need than a 169-day Anchorage one.
- The care engine reads actual rainfall: a genuinely dry three-day outlook
  raises "check soil moisture" tasks, and expected rain suppresses watering.

Still a placeholder: frost dates come from a **single recent year**, which is
noisy — one mild winter shifts them. A real version should use a 10-30 year
normal (Open-Meteo's climate API, or NOAA/PRISM normals) and express it as a
probability. The `build_tasks()` rules should also consider soil moisture and
growing-degree-days accumulated since planting, not just days elapsed.

### 5. Supabase / PostgreSQL
Two places:

- **Crop data** — `backend/services/crop_repository.py`. Every caller goes
  through `all_crops()` / `get_crop()`, so replacing the JSON read with a
  Supabase query touches nothing else.
- **User state** — `frontend/lib/store.tsx`. The `localStorage` read/write in
  the two `useEffect` hooks becomes Supabase reads/writes keyed by user id. The
  `GardenState` shape already maps onto a table per section:

  ```
  households        (id, size, created_at)
  food_profiles     (household_id, meals, free_text, ingredients)
  growing_spaces    (household_id, location, zip, width_ft, length_ft, sunlight, …)
  recommendations   (household_id, summary, crops)
  layouts           (household_id, plot, plants, beds, paths)
  plantings         (layout_id, crop_id, planted_on, status)
  ```

  Auth0 is already wired (`session.user.sub` is the user id). Persistence is
  still `localStorage` until this swap.

### 6. Computer vision
`frontend/components/space/GrowingSpaceForm.tsx` has a disabled photo-upload
placeholder. Image analysis (estimating usable area and sun exposure from a
yard photo) would become a fifth service, `services/space_analysis.py`, with
its own endpoint. Do not fold it into the existing four.

## API contracts

All five endpoints are typed on both sides:
`backend/models/schemas.py` ↔ `frontend/lib/types.ts`. There is no codegen
step — change one, change the other.

```
GET  /api/location              ?city&zip               → LocationLookupResponse
POST /api/analyze-food          AnalyzeFoodRequest      → AnalyzeFoodResponse
POST /api/recommend-crops       RecommendCropsRequest   → RecommendCropsResponse
POST /api/generate-layout       GenerateLayoutRequest   → GenerateLayoutResponse
GET  /api/garden-status         ?day&location&zip       → GardenStatusResponse
GET  /api/care-recommendations  ?location&zip&crops     → CareRecommendationsResponse
GET  /api/crops                                         → raw crop dataset
GET  /api/health
```

Example:

```bash
curl -s localhost:8000/api/analyze-food -H 'content-type: application/json' -d '{
  "household_size": 4,
  "meals": [{"name": "Tacos", "times_per_week": 2}],
  "free_text": "We make tacos twice a week and salads for lunch."
}' | python3 -m json.tool
```

## Frontend notes

**Screens** — `/` landing, `/onboarding/food`, `/profile`,
`/onboarding/space`, `/recommendations`, `/garden`, `/garden/3d`, `/today`,
`/account` (Auth0 session).

**Components** — grouped by feature: `layout/` (nav, progress header),
`ui/` (primitives, icons), `food/` (MealInput, IngredientCard,
FoodDemandChart), `space/` (GrowingSpaceForm, PlotPreview),
`recommendations/` (CropRecommendationCard, RecommendationScore,
SavingsSummary, HomegrownCoverageCard), `garden/` (GardenGrid, PlantMarker,
PlantDetailsPanel, Garden3D, PlantModels), `today/` (WeatherCard,
GardenTaskCard).

**3D** — React Three Fiber + drei, imported with `next/dynamic({ ssr: false })`.
There are no 3D assets: no GLTF, no textures, nothing downloaded. Every plant
is procedural geometry built in `plantGeometry.ts` — bezier leaf outlines
sculpted into a cupped, drooping blade, stems swept along curves, squashed
fruit with a calyx. Six archetypes (vine, bush, herb, rosette, spike, sprawl)
cover all ten crops, and each plant is varied by a seed hashed from its id
(`lib/random.ts`) so neighbours differ in lean, leaf count, size and tint
without the scene becoming non-deterministic. Photorealism is not the goal;
telling the crops apart at a glance is.

**Animation** — all of it is procedural and runs from a single `useFrame` loop
that mutates object refs directly. Nothing re-renders React per frame, which is
what keeps ~80 plants at 60fps+ (measured 120fps at full maturity):

- **Season time-lapse.** A scrubber and a play button drive a `clockRef` the
  render loop reads. Each plant scales from seedling to mature on an eased
  curve against its own `days_to_harvest`, and its fruit group scales up from
  zero over the last 38% of that run. Per-crop progress bars and a "ready to
  harvest" readout sit under the canvas.
- **Wind sway.** Two offset sines per plant with a seeded phase, amplitude
  scaled by mature height, so a tomato moves and a lettuce barely does.
- **Sun arc.** A time-of-day slider sweeps the directional light east to west,
  warming its colour near the horizon and scaling intensity by the sun exposure
  the user entered for the plot.
- **Camera.** Eases in from a wide shot on load, and glides its orbit target to
  a plant when you click one.
- **2D.** Plants stagger into the planner (`animate-pop`, delay capped so a big
  garden still fills quickly) and the headline metrics count up from zero.

**Reduced motion** — `usePrefersReducedMotion` switches off sway, camera
easing, autoplay and count-ups, and a global CSS rule collapses every
transition and entrance. The season scrubber still works: it is user-driven,
not unsolicited movement. `useCountUp` also snaps straight to its target in a
hidden tab, since browsers pause `requestAnimationFrame` in the background and
a metric frozen at "$0" is worse than one that never animated.

**Design tokens** — in `tailwind.config.ts`: cream background, forest-green
ink, moss accents, sage surfaces, small amounts of terracotta. Fonts are system
stacks so the app builds and runs with no network access.

### A note on sunlight

There is deliberately **no "how sunny is your yard" input**. It was a
self-reported guess presented as data: three coarse buckets, no way to check
them, and it fed a `sunlight_hours` comparison that implied far more precision
than existed. Local climate — frost dates, degree-days, summer temperatures —
is measurable and now does that work instead.

`sunlight_hours` remains in `crops.json` because it is a real property of each
crop. It is simply unused until there is something real to compare it against:
the photo-upload placeholder in the growing-space form is where a measured sun
exposure would come from, and `crop_scoring._climate_fit()` is where it would
slot back in.

## Known limitations

- The plant allocator and the layout packer are separate systems (by design),
  so the allocator can occasionally recommend slightly more plants than the
  packer can place. The overflow is reported in `unplaced` and shown in the UI
  rather than hidden.
- Crop yields, retail prices and costs are rough placeholders. Do not present
  the savings figures as real numbers.
- Homegrown coverage assumes 7 lbs of produce per person per week over a
  20-week season. That constant lives in `crop_scoring.py`.
- No server-side persistence. Auth0 identifies the user; garden state is still per-browser `localStorage`.
