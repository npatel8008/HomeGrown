## Your mission

This repo is **GardenAI**: a working hackathon scaffold that turns a household's
food habits into a personalized backyard garden plan (which crops, how many,
where they go, what they save). Read `README.md` first — it is accurate and
describes the architecture honestly.

Your job is to **re-center the product on two features** and make them the thing
a judge sees in the first fifteen seconds:

1. **Your garden, in the real world.** A phone-first, Pokémon-Go-style AR view:
   live camera feed, the planned garden anchored to a real place and a real
   compass heading, plants standing in the yard at true scale, tap a plant to
   inspect it, walk up to a plant to "encounter" it.
2. **Talk to your garden.** An **ElevenLabs** voice layer that listens, answers
   out loud, and *actually edits the plan* — moving plants, swapping crops,
   changing counts, regenerating the layout — while you are standing in the AR
   view looking at it.

Everything already in the repo (food profile → recommendations → layout → 3D →
today) stays working. You are adding a new spine and re-pointing the app at it,
not rewriting the product.

## What already exists (verify, don't trust this summary blindly)

**Backend** — FastAPI, `backend/`. Thin routes that delegate to `services/`.
Four deliberately independent systems:

| System | Module | Endpoint |
|---|---|---|
| Ingredient extraction | `services/ingredient_extraction.py` | `POST /api/analyze-food` |
| Crop scoring / allocation | `services/crop_scoring.py` | `POST /api/recommend-crops` |
| Layout generation | `services/layout_generator.py` | `POST /api/generate-layout` |
| Care / weather | `services/care_engine.py` | `GET /api/garden-status`, `GET /api/care-recommendations` |

- `services/llm_client.py` — OpenAI-compatible client for IFM/K2, with retries,
  JSON extraction, and `None` on failure meaning "use the offline path".
- `services/location.py` + `services/climate.py` — **live, keyless Open-Meteo**
  geocoding, frost dates, growing-degree-days and forecast, behind
  `GET /api/location`. `crop_scoring.py` scores against this real climate and
  `care_engine.py` builds tasks from the real forecast, so weather is no longer
  mocked. Both need outbound network and fall back offline when they don't have
  it.
- `services/crop_repository.py` — reads `data/crops.json`.
- `models/schemas.py` — Pydantic contracts, **hand-mirrored** in
  `frontend/lib/types.ts`. No codegen. Change one, change the other.
- `GET /api/health` reports, per system, whether a real model or a mock ran.

**Frontend** — Next.js 14 App Router + TypeScript + Tailwind, `frontend/`.

- `components/garden/Garden3D.tsx` — React Three Fiber scene (`three` 0.169,
  `@react-three/fiber` 8.17, `@react-three/drei` 9.114) rendering the layout
  JSON: ground, beds, paths, plants, `OrbitControls`, hover billboards. **It is
  animated**: one `useFrame` loop mutates object refs directly and reads a
  `clockRef` (`SceneClock`: day of season + time of day) that
  `components/garden/SceneControls.tsx` writes into. Nothing re-renders React
  per frame — that is deliberate, and it is what keeps ~80 plants at 60fps.
  Preserve this property in anything you build on top of it.
- `components/garden/PlantModels.tsx` + `plantGeometry.ts` — low-poly archetypes
  sized from each crop's mature height and grown from a seedling scale.
- `lib/motion.ts` (easing, `usePrefersReducedMotion`), `lib/random.ts`
  (`plantVariation`, seeded so plants don't jump between renders).
- `lib/selection.ts` — `summarizeSelection()` recomputes the garden summary from
  the crops the user has ticked, client-side. Crop selection already exists; do
  not build a second one.
- `lib/store.tsx` — React context + `localStorage` (`gardenai.demo.v1`) holding
  household, ingredients, space, recommendations, layout, offline flag.
- `lib/api.ts` — every call falls back to `lib/fallback.json` and reports
  `usedFallback` so the UI can say so.
- `components/ui/EngineBadge.tsx` — the existing "generated by X" badge pattern.

**Layout coordinate system (important for AR):** the backend emits feet, origin
at the plot's near corner, `x` across the width and `z` along the length;
`Garden3D` re-centers with `x - width/2`, `z - length/2`. Keep that as the only
place the plot is centered, and convert feet → meters exactly once (× 0.3048).

## Non-negotiable constraints

1. **Keep the repo's honesty contract.** Every new model-, sensor-, or
   network-backed path needs a deterministic fallback and a visible badge saying
   which one ran. The app must never claim AI or AR that didn't happen, and must
   never hard-fail mid-demo. Extend `/api/health` with the new systems.
2. **Keep the systems separate.** Do not bolt voice or AR logic onto the four
   existing services. New concerns get new modules (see the file map below).
   Routes stay thin: validate, delegate, return.
3. **Contracts stay mirrored.** Any new Pydantic model gets a matching interface
   in `frontend/lib/types.ts` in the same commit.
4. **No secrets in the browser.** The ElevenLabs API key lives only in the
   backend. The client gets a short-lived session token / signed URL.
5. **One mutation path.** Voice is *a caller of* the garden-command layer, never
   a second way to mutate state. Every voice action must also be reachable from
   a button, so the whole feature is demoable and testable with no microphone.
6. **Mobile-first.** The AR view is designed for a phone held in portrait, one
   thumb, outdoors, in sunlight. Desktop gets a usable dev harness, not the
   primary experience.
7. **Don't regress the existing flow.** `/onboarding/food`, `/onboarding/space`,
   `/recommendations`, `/garden`, `/garden/3d`, `/today` keep working, and
   `npm run typecheck`, `npm run build`, and the offline fallback path all keep
   passing.
8. **Reuse the scene graph.** The AR view and the orbit view must render the
   *same* plant models and the *same* layout JSON. Extract, don't duplicate.
9. **It has to run on a stranger's phone.** The demo target is a judge's own
   device, opened from a QR code, no install, no app store, no laptop tether, on
   conference wifi or cellular. That means a public HTTPS origin for *both*
   frontend and backend, state seeded on cold start, and every permission denial
   degrading to something still worth looking at. Phase 0 exists to make that
   true before any feature work starts.

## Phase 0 — A URL that works on a phone you don't own (do this first)

Deploy the app **as it is today**, before writing a single new feature, and keep
every later phase deployed as you go. A feature that only runs on your laptop
does not exist at judging time, and discovering a hosting problem at 4pm costs
you the demo, not just the afternoon.

- **Frontend:** Vercel, with `frontend/` as the project root. **Backend:** any
  HTTPS host with a free tier (Render, Fly, Railway), *or* a named Cloudflare
  tunnel from your laptop if you would rather the API keys never leave it. Either
  is fine; both must be HTTPS.
- **The mixed-content trap — read this twice.** An HTTPS frontend cannot call
  `http://localhost:8000` or `http://192.168.x.x:8000`. The browser blocks it,
  `lib/api.ts` catches the failure, and the app silently drops into
  `fallback.json` offline mode — which *looks like it is working*. You will not
  notice until voice mysteriously fails on stage. So: backend on HTTPS,
  `NEXT_PUBLIC_API_URL` pointed at it, deployed frontend origin added to
  `ALLOWED_ORIGINS`, and confirm on the phone that the badge says live and not
  "Offline demo mode".
- **QR code.** Generate one for the deployed URL (including `?demo=1`, see
  below), commit it to `docs/`, and put it on a page the laptop can display
  full-screen. Judges scan; they do not type URLs.
- **Cross-device test matrix, before you need it:** one iPhone on Safari, one
  Android on Chrome, and one phone on **cellular rather than wifi** (conference
  networks block and throttle in creative ways). Record what you actually tested
  in `docs/DEMO.md` — untested devices are unproven devices.
- **Weigh the bundle.** three.js plus drei over shared conference wifi is a real
  wait. Keep the dynamic-import pattern the repo already uses, check the AR
  route's transferred bytes under throttling, and make the loading state say what
  it is doing rather than showing a bare spinner.
- **Confirm the offline path still saves you:** with the backend stopped, the AR
  view must still render from `fallback.json` and say so honestly.

**Acceptance:** you hand your unlocked phone to someone else, they scan the code,
and the garden appears — with no words from you and nothing plugged into your
laptop.

## Phase 1 — Shared scene, and an AR shell that works

Refactor `Garden3D.tsx` so the scene *content* (ground/beds/paths/plants/
selection) is a standalone component that knows nothing about the camera,
background, or input source. Keep the existing `useFrame` + `clockRef`
animation intact and keep it ref-driven — if you convert growth animation to
React state while extracting, you will drop the scene to single-digit fps on a
phone, which is the one device that matters here. The season scrubber should
keep working in AR. Then build three presentation modes over it:

- **`orbit`** — today's behavior, unchanged, at `/garden/3d`.
- **`geo`** — camera passthrough AR (the default on phones). Full-screen
  `<video autoPlay muted playsInline>` from `getUserMedia({ video: { facingMode:
  "environment" } })` behind a transparent-canvas R3F scene.
- **`xr`** — real WebXR `immersive-ar` with hit-testing, used only where
  `navigator.xr?.isSessionSupported("immersive-ar")` resolves true.

New route `/garden/ar`, and make it the primary CTA: landing page hero, nav
entry, and a big "See it in my yard" button on `/garden` and `/recommendations`.

Two AR scales, both required — pick with a visible toggle:

- **Life-size** — 1:1, for standing in an actual yard.
- **Tabletop** — the whole plot scaled to about 1:12 and dropped on the floor or
  a table in front of you. *This is the one you will actually demo indoors at a
  hackathon.* Do not treat it as an afterthought.

**Acceptance:** on a phone over HTTPS, `/garden/ar` shows the live camera with
the planned garden composited over it, plants tappable, at both scales; on a
desktop browser the same route falls back to the orbit scene with a clear
"camera unavailable — showing the 3D view" notice; `/garden/3d` is visually
unchanged.

## Phase 2 — Pokémon-Go-style anchoring

Anchor the plot to the real world in `geo` mode using sensors, not SLAM:

- **Origin capture.** A "Set my garden here" action captures
  `{ lat, lng, heading, capturedAt }` from `navigator.geolocation` plus the
  current compass heading, persists it in the store, and defines the plot's near
  corner. Offer "re-anchor" and "nudge rotation" controls — heading drift is the
  single most likely thing to embarrass you on stage.
- **Camera orientation** from `DeviceOrientationEvent`. On iOS you must call
  `DeviceOrientationEvent.requestPermission()` from inside a user gesture, and
  read `webkitCompassHeading` for true heading; on Android prefer
  `deviceorientationabsolute` and correct `alpha` by `screen.orientation.angle`.
  Apply a low-pass filter — raw readings jitter badly.
- **Geo → scene meters**, equirectangular approximation around the origin:
  `dx = (lng - lng0) * 111320 * cos(lat0)`, `dz = -(lat - lat0) * 110540`.
  Plenty accurate over a 12 ft plot.
- **Pokémon-Go feel, in priority order:** billboarded crop labels that always
  face the user; a proximity "encounter" card that slides up when you are within
  ~1 m of a plant (harvest countdown, yield, value, today's care task from
  `/api/care-recommendations`); a bottom radar/minimap showing plants around you
  with a heading cone; day/night scene lighting from device time; a tap-to-inspect
  detail sheet reusing `PlantDetailsPanel`; a share/screenshot button that
  composites camera + canvas to a PNG.
- **Dev harness.** `?ar=sim` injects synthetic orientation and geolocation and
  drives the camera with WASD/drag so the entire AR view can be built and
  debugged on a laptop with no phone and no camera. Build this early; it will
  save you hours.

**Performance budget:** cap `dpr` at `[1, 1.5]` on mobile, disable shadows in AR
modes, instance plant meshes once the count passes ~40, stop rendering when the
document is hidden, and keep the video element muted and inline.

**Acceptance:** standing in one place and turning around, plants stay put in the
world within a few degrees; walking toward a plant triggers exactly one encounter
card; `?ar=sim` reproduces all of it on desktop.

## Phase 3 — The garden-command layer (do this before touching voice)

This is the spine. Define one command vocabulary that every editor — voice,
button, drag in the 2D planner — flows through.

In `frontend/lib/types.ts` (mirrored in `backend/models/schemas.py`):

```ts
export type GardenCommand =
  | { kind: "move_plant"; plant_id: string; to: { x: number; z: number } }
  | { kind: "remove_plant"; plant_id: string }
  | { kind: "add_plants"; crop_id: string; count: number }
  | { kind: "set_crop_count"; crop_id: string; count: number }
  | { kind: "swap_crop"; from_crop_id: string; to_crop_id: string; count?: number }
  | { kind: "exclude_crop"; crop_id: string; reason?: string }
  | { kind: "pin_crop"; crop_id: string }
  | { kind: "regenerate_layout"; note?: string }
  | { kind: "set_space"; patch: Partial<GrowingSpace> }
  | { kind: "focus_plant"; plant_id: string }
  | { kind: "undo" };

export interface GardenCommandResult {
  ok: boolean;
  applied: GardenCommand[];      // what actually happened (may differ from asked)
  message: string;               // one or two sentences, written to be SPOKEN
  warnings: string[];            // "that pushes you $12 over budget"
  layout?: GenerateLayoutResponse;
  recommendations?: RecommendCropsResponse;
  generated_by: string;
}
```

Backend: new `services/garden_commands.py` + `routes/voice.py`-adjacent
`POST /api/garden-command`. It applies commands **deterministically** against the
posted layout/recommendations and validates them: stay inside bed bounds, respect
each crop's `spacing_ft`, snap to a sane grid, refuse overlaps, report budget and
area overruns as `warnings` rather than silent truncation. Share the bed geometry
and spacing helpers with `layout_generator.py` by extracting them — do not
copy-paste, and do not make layout generation depend on editing.

Crop *choice* changes have two layers, and you need both. Ticking a crop on and
off is already client-side in `lib/selection.ts` — `set_crop_count` and
`exclude_crop` should drive *that* existing mechanism and its store state rather
than a parallel one. But changes that need re-ranking or re-allocation must go
back through the real recommender, not be faked in the response: add optional `pinned_crop_ids` and `excluded_crop_ids` to
`RecommendCropsRequest` (backward compatible, default empty) and have
`crop_scoring.py` honor them. "I hate kale, give me more tomatoes" should
genuinely re-score and re-allocate.

Frontend: a `applyCommand(command)` action on the store that calls the endpoint,
applies the result, and maintains an **undo stack** (at least 10 deep). Add a
visible command log panel — every applied command as a readable line with an undo
button. That panel is what proves to a judge that the voice did something real.

**Acceptance:** with the mic never enabled, buttons alone can move a plant, swap
a crop, change a count, exclude a crop, regenerate, and undo — and both the 2D
planner and the AR view update from the same state.

## Phase 4 — ElevenLabs voice

**Check the current ElevenLabs docs before writing the integration** (WebFetch
`elevenlabs.io/docs`) — package names and endpoint shapes move faster than
anyone's memory. Do not guess a voice ID; make it configurable.

Primary path — **ElevenLabs Agents (conversational AI)** with client tools:

- Backend `GET /api/voice/session` (in `routes/voice.py`, logic in
  `services/voice_agent.py`) returns a short-lived signed URL / conversation
  token minted with `ELEVENLABS_API_KEY` + `ELEVENLABS_AGENT_ID`. The key never
  reaches the browser. Return a clear, typed error when unconfigured.
- Frontend uses the official React SDK (`@elevenlabs/react`, `useConversation`)
  and registers **client tools that map 1:1 onto `GardenCommand`** plus a couple
  of read-only ones: `get_garden_summary`, `list_plants_of_crop`,
  `explain_recommendation`. Each tool returns the `GardenCommandResult.message`
  so the agent can speak the real outcome instead of inventing one.
- **Ground the agent in the actual garden.** At session start, and after every
  applied command, pass a compact snapshot as dynamic variables/context: plot
  dimensions, garden type, crop names with counts and plant-id ranges, the
  savings summary, budget headroom, and the currently focused plant. Keep it
  small — never dump the full plant array.
- Agent persona: a concise, practical gardener. Short answers. Confirms before
  destructive edits ("that removes all four kale — want me to?"). Speaks numbers
  the app actually computed. Never invents crops outside `data/crops.json`.
  Keep the system prompt in the repo (`backend/prompts/voice_agent.md`) even if
  the dashboard also holds a copy, and document any required dashboard setup in
  the README so someone else can reproduce the demo.

Fallback chain, each with its own badge value (reuse `EngineBadge`):

1. `elevenlabs-agent` — the above.
2. `elevenlabs-stt+k2+tts` — record audio → ElevenLabs speech-to-text →
   `llm_client.complete_json()` with a terse prompt that maps the transcript onto
   a `GardenCommand[]` → apply → ElevenLabs text-to-speech for the reply
   (streamed through the backend, not fetched directly from the browser).
3. `browser-speech` — Web Speech API recognition + `speechSynthesis`.
4. `text` — a plain text input that runs the same interpreter. Always available.

**Interaction rules, all required:**

- **Push-to-talk by default** (hold the mic button). A hackathon room is loud;
  always-on VAD will trigger on the judge next to you. Offer hands-free as an
  opt-in toggle.
- **Captions always.** Render the live user transcript and the agent's spoken
  reply as text. Half your audience will not hear the audio.
- **Optimistic + reconciled.** Apply the local geometry change immediately so the
  AR view reacts while the agent is still talking, then reconcile with the
  server result. Keep tool round trips under ~400 ms.
- A visible mic state (idle / listening / thinking / speaking), a mute button,
  and a hard "stop" that tears the session down.

**Acceptance:** standing in the AR view, saying "move the tomatoes to the back
row", "swap the kale for spinach", "add two more pepper plants", "that's too
much, undo", and "why did you pick basil?" each produce the correct visible
change plus a spoken reply describing what actually changed — and with
`ELEVENLABS_API_KEY` unset, the text-input path does all the same edits with the
badge saying so.

## Demo-day reality: several phones, none of them yours

Design for this from the start; it is not polish.

- **Cold start.** A judge's phone has empty `localStorage`. The QR link's
  `?demo=1` must seed household → recommendations → layout, auto-anchor a
  tabletop garden, and land on `/garden/ar` with the mic button live. No
  onboarding, no typing, no back-navigation. Re-test it in a fresh private window
  every time you change the store shape — this is the single most fragile path in
  the demo.
- **Concurrency.** Several people may scan at once. Keep the backend services
  free of global mutable state, and know your **ElevenLabs concurrent-session
  cap** — the lower plan tiers are small. When it's hit, return a clean "voice is
  busy right now, here's the text input" result. A 429 must never surface as a
  crash or a silent dead mic.
- **Permission denial is the normal case, not the edge case.** A stranger will
  tap "Don't Allow" at least once. Camera denied → the orbit 3D garden. Motion
  denied → drag-to-look. Location denied → tabletop mode. Mic denied → the text
  command box. Each with one plain sentence about what they're missing and a
  button to retry.
- **iOS specifics you must verify on real hardware:** Settings → Safari → Motion
  & Orientation Access can be switched off, in which case
  `DeviceOrientationEvent.requestPermission()` rejects — that must produce
  drag-to-look, not a frozen scene. Low Power Mode throttles the render loop, so
  don't depend on 60fps. Never ask a judge to "Add to Home Screen".
- **Plan C, recorded early.** As soon as the AR + voice flow works end to end,
  record a 60-second screen capture of it on a real phone and commit it to
  `docs/`. It plays with no network, no permissions, and no luck. Record it the
  day it starts working, not the night before.

## Environment and local testing

Add to `backend/.env.example`, all optional with documented fallbacks:

```
ELEVENLABS_API_KEY=
ELEVENLABS_AGENT_ID=
ELEVENLABS_VOICE_ID=
ELEVENLABS_MODEL_ID=
```

Also set `NEXT_PUBLIC_API_URL` (frontend) and `ALLOWED_ORIGINS` (backend) to the
deployed HTTPS origins, not localhost.

Camera, microphone, motion, and geolocation all require a **secure context**, so
`http://<laptop-ip>:3000` will never work from a phone. Two setups, and you need
both documented in the README:

- **Local development on a phone:** `next dev --experimental-https`, or a tunnel
  (`cloudflared tunnel --url http://localhost:3000`, `ngrok http 3000`) with the
  backend tunneled too and its origin allowlisted.
- **The demo itself:** the Phase 0 deployment — a stable public URL that does not
  depend on your laptop being awake, on the same network, or on a tunnel process
  that has been running for nine hours.

**Verify before you call anything done:**

```bash
cd frontend && npm run typecheck && npm run build
cd ../backend && uvicorn main:app --port 8000   # then exercise the new endpoints with curl
```

Then, in this order:

1. The `?ar=sim` harness on desktop.
2. A real iPhone and a real Android on the **deployed** URL, not a tunnel.
3. One of them on cellular instead of wifi.
4. A full run with the backend stopped, confirming offline mode still reaches the
   AR view and says so.
5. The handoff test: give the QR code to someone who has never seen the app, say
   nothing, and watch where they get stuck. Fix that.

## Decide these yourself — do not stop to ask

Sensor-AR (camera + compass + GPS) over any paid AR SDK. Tabletop scale as the
indoor default. Push-to-talk as the default mic mode. Snap-to-grid on
`move_plant`. Undo depth of 10. Voice replies capped at roughly two sentences.
Anchor persisted in `localStorage` alongside the existing state. If a detail is
unspecified, pick the option that is most likely to survive a live demo and write
down the choice.

**Do stop and ask** only if: there is no way to obtain ElevenLabs credentials
(then build the full fallback chain and text path, and wire the Agents path
behind the config flag); or a requirement here genuinely contradicts something
you find in the code.

## How to work

Go in the phase order above — deployment before features, the command layer
before the voice layer, the sim harness before the phone work. Commit at the end of each phase with a message
naming the phase; do not push. Keep the existing code's voice in new files:
module docstrings that explain *why*, `>>> REPLACE ME <<<` markers on anything
still faked, no decorative comments.

When you finish, report: the deployed URL and the QR asset's path, which real
devices and networks you actually tested on, what works end to end, what is still
mocked and where, every new env var, the exact steps to run the demo from a cold
phone, and anything you could not verify without hardware you did not have. Be blunt about the last one — an
unverified AR claim is worse than a known gap.
